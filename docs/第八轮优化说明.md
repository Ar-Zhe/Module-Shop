# 第八轮优化说明（功能 1/3/4/5/6/7/8/9 · 界面版式复查）

本批两件事：**按选定的 1/3/4/5/6/7/8/9 项做功能优化**，以及**逐界面复查版式**（字体过大 / 按钮与文字重叠 / 输入框看不出能输入 / 字体重影）。

## 一、功能优化（1、3、4、5、6、7、8、9）

1. **「全部领取」不再整批拦截**：金额**先到账**（金额不占背包），物品**逐封尝试**放入背包；装不下的那几封**原样留在邮箱**（不消耗邮件、不销毁物品），并在聊天栏提示「还缺几格、清理背包后可再点全部领取」（`msg.server_shop_mod.claim_all_partial`）。**单封领取**仍然先算背包空间，放不下直接拦截且不消费邮件。
3. **补签二次确认**：点可补签日期先弹确认框（`ConfirmScreen`），显示**补签日期**与**花费星币**，确认后才扣费补签，取消则回日历——避免误点直接扣钱。
4. **「删除该日程」入口调整**：删除按钮从「日程奖励」界面**移到日程编辑界面底部**（红色按钮，紧挨「日程奖励」），确认后清空该日程并回签到日历；日程奖励界面不再有删除按钮，避免「改奖励时手滑删日程」。
5. **每日商店长条模式显示进度**：牌数超过 6 张改为一行一张的长条后，右侧显示 `当前 / 总数`（`daily_pos`），滚轮整行滚动时同步更新。
6. **兑换码生成器提示发放方式**：底部提示「奖励将以邮件形式发放（邮箱满时自动转背包 / 掉落）」（`redeem.mail_hint`），管理员生成前就知道兜底规则。
7. **日程新增「错过即补发」开关**：定时发放的日程，若玩家在设定时间点之后才登录，**当天内仍补发一次**；与「补发离线玩家」相互独立（前者管当天迟到的在线玩家，后者管离线玩家）。
8. **收购全清奖励可见**：管理员界面的奖励行显示**当前生效的奖励金额**（`buyback_bonus_value`），改配置时不用靠猜。
9. **星币上限提示 + 上限调大**：余额到上限时顶栏余额后显示「（已满）」（`balance_full`）；`maxBalance` 默认值由 `999,999,999` 提高到 `9,999,999,999`，并由 `ConfigMigration` 把**旧默认值**自动迁移为新值（服务端只替换 jar 即可生效）。

## 二、界面版式复查（本批重点）

### 全局约定（之后新增界面一律遵守）

* **统一小字号**：字段标签统一用 **0.8 倍**缩放绘制，不再出现大字压住边框或压住输入框。
* **输入框必须看得见**：`EditBox` 关掉自带黑底（`setBordered(false)`），改画统一底框（`FIELD_BG` + 描边，**聚焦时蓝色描边**）；并且**在面板绘制完成后重画一次控件**——此前是「先画控件、后画面板」，输入框被面板整块盖住，玩家根本看不出哪里能输入，这是「输入框看不出来」的根因。
* **分区标题画在分区盒子外侧上方**，盒子内只放字段行；字段一律**左标签 + 右控件**横向分离，纵向不可能重叠。
* **字体重影**：不再手动画第二遍输入框文字（此前 `drawString` 与 `EditBox` 自身文字叠加，看起来就是重影）。

### 逐界面

* **日程编辑界面** `ScheduleEditScreen`（396×216）：内容区（标题 / 公告正文）+ 外观区（色板缩小，去掉占高度的颜色预览行）+ 底部 `[日程奖励] [删除该日程] …… [取消] [保存]`；未填标题时保存置灰并红字提示「请先填写标题」。
* **日程奖励界面** `ScheduleRewardScreen`（396×278）：发放规则三行（**定时发放** + 读数框 + 「选择时间」弹窗 / **补发离线玩家** 开关 / **错过即补发** 开关）+ 奖励区（星币 `−` 输入框 `+`、日程物品、额外物品），底部取消 / 保存；时间选择弹窗补充「按 ESC 返回上一级」提示。
* **物品选择器**（点「添加物品」进入）：按**物品发放界面**的样式重做 —— **左侧物品格子网格**（10×7，左键 `+1`、右键 `+8`、滚轮翻页）、**右侧深色列表面板**（搜索框 + 已选物品行：物品图标 + 名称 + `×数量` + `✕` 移除，底部「清空 / 确认」）。**去掉了全体玩家 / 全不选等玩家相关按钮**；**ESC 先关选择器回到上一级**（再按一次 ESC 才退出日程奖励界面）。搜索列表带缓存，避免每帧重建上千个 `ItemStack` 掉帧。
* **签到界面** `SignInScreen`（380×276）：**右下角新增「返回」按钮**（单独一行，与管理员按键不重叠）；**管理员按键行整体上移一行**；「编辑」改名「**启动编辑**」；日历格子高度 20 → 18 给底部让位；**鼠标移到里程点显示「连续签到加成：X星币」**（取不超过该里程天数的最高累计档位）。

## 三、服务端与配置

* 玩法配置（签到、日程、兑换、刷新参数、收购奖励）依旧全部存在**存档 SavedData**，新增字段老存档自动取默认值。
* `ConfigMigration` 负责旧默认值迁移：邮箱上限 `50 → 100`、货币名 `金币 → 星币`、余额上限 `999999999 → 9999999999`（仅命中旧默认值时才改）。
* 结论：**服务端只需替换 `server_shop_mod-1.15.0.jar`**，无需手动改配置文件；客户端需装同一个 jar。

## 四、第二轮反馈修正（同日）

1. **兑换码随机码去掉固定前缀**：原来生成 `WUWA-XXXX-XXXX-XXXX`，现在直接随机 `XXXX-XXXX-XXXX`（字母表仍剔除易混字符 I / O / 0 / 1）。
2. **面板高度适配 GUI 缩放**（「上面字体跑出 UI」的根因）：1920×1080 客户端自动 GUI 缩放为 **480×258**，而日程奖励设置原高 278、签到界面原高 276 都**超过屏幕高度**，`top()` 被算成负数、面板被裁掉，标题就跑到面板外面去了。现在统一收紧：日程奖励设置 **278 → 216**、签到界面 **276 → 246**，日程编辑 216、日程奖励（物品）236（与物品发放同尺寸），标题与底部按钮都稳稳在面板内。
3. **日程奖励改为「物品发放」式界面**（把发放的逻辑直接带过来）：
   * 日程奖励设置界面里，奖励区**只留一个「日程奖励」按钮**；删掉了「当天奖励（星币）」「日程物品」「额外物品」三行，以及点开它们才出现的弹窗选择器。
   * 点它打开的是**与物品发放同一套逻辑的容器界面**（复用 `GrantMenu`：3×9 真实物品槽 + 管理员背包 + 金额输入），右侧显示该日程当前奖励，底部「保存 / 取消」。
   * 打开时**把当前奖励预填进格子**，可以直接增减或替换物品。
   * 关闭 / 取消时**只退还管理员自己放进去的那部分**，预填的旧奖励不会被退成实物 —— 既不会丢东西，也不会复制物品；保存时服务端先清空槽位再落库。
   * 服务端 `ActivityDay` 新增 `rewards` 物品列表（老存档的 `item` / `gift` 在载入时自动并入），发奖整包走邮箱；奖励改动会清掉「已领取」记录，保证新奖励重新发一次。
   * 「日程奖励设置」保存时**不再覆盖奖励**（只写公告 / 颜色 / 时间 / 开关），服务端对未携带的字段保持原值。
4. **邮箱详情的「附件 / N 天后自动删除」不再重叠**：这两处文字原来画在几乎同一坐标（`附件` 在 `cy+paneH-69`、到期提示在 `cy+paneH-70`，都在 `dx+8`），看起来就是一团字叠在一起。现在到期提示**右对齐**到「附件」同一行的右侧（红色），标题与物品名超出宽度会**自动省略号**，正文换行高度也限制在附件标题上方，短窗口下同样不会压行。

## 五、第三轮反馈修正（同日）

1. **日程标题 / 正文保存修复**：根因是「日程奖励设置」界面会用它**打开时捕获**的标题回写服务端 —— 如果先点了「日程奖励」再回填标题，标题就被空值覆盖成 `(日程)`。现在改成**每个界面只写自己负责的字段**：
   * 「日程编辑」写标题 / 正文 / 颜色；
   * 「日程奖励设置」只写定时发放 / 补发离线 / 错过即补发；
   * 「日程奖励」（物品发放式容器）只写星币与物品。
   服务端对**未携带的键一律保持原值**，谁都不会覆盖别人的编辑；并且点「日程奖励」按钮时会**先把标题/正文/颜色存一次**，绝不会出现「只配了奖励、公告丢了」。
2. **签到悬浮窗改成从上到下**（按图三的顺序）：① 最上面标题 → ② 中间正文（0.8 倍小字自动换行）→ ③ **金额：0.8 倍小字 + 金色**，放在物品上面 → ④ 最下面奖励**物品图标**（带数量角标，图标上悬停可看完整名字）。服务端额外下发 `itemIds`（可解析的物品 id 列表），客户端据此画图标。
3. **同一渠道的邮件自动合并**（防止"一件物品一封邮件"把邮箱塞满）：
   * `MailEntry` 支持**一封邮件装多件物品**（`stacks` 列表，老存档的 `stack` 载入时自动并入）；
   * 一次发放（活动奖励 / 管理员发放 / 摊位售出等）只产生**一封**邮件，所有物品都在里面；
   * 入库时若已存在**来源 + 业务类型 + 标题 + 正文完全相同且尚未领取**的邮件，新物品/金额直接**并进那一封**（同种物品还会自动叠成一组），不再新开；
   * 领取 / 全部领取按整封邮件逐件放入背包，放不下的整件留在邮件里。
4. **修掉「编辑日程时被直接弹出界面」**（"输入标题后就不能添加物品了"的根因）：客户端收到普通快照时的原逻辑是「当前不是商店界面 → 直接换成商店界面」，于是管理员在日程编辑 / 签到里一点按钮（服务端回推快照）就被弹到商店界面，编辑中断、看起来像"没保存"。现在**只有玩家当前没有任何界面打开时**才自动拉起商店主界面（例如 `/shop`），其它情况只刷新缓存、绝不打断当前界面。
5. **邮箱附件改成「格子」展示**：不再写物品名，而是一排**物品格子**（按面板宽度最多 8 列 × 2 行），每格只放图标 + 数量角标，悬停看完整信息；物品超过一屏时**鼠标滚轮整行上下滑动**（与收购 / 货币兑换列表同一套滚轮逻辑：鼠标在格子上才滚附件，否则仍然是翻邮件列表），右侧显示上下小箭头提示还有内容。
6. **修复「配了 4 件物品，邮件里只显示 1 件」**：邮箱快照是**手写序列化**的，漏掉了新的附件列表字段（只下发了第一件），所以服务端明明有 4 件、客户端只画得出 1 件 —— 现在快照把整份附件列表一并下发。同时把星币与物品的「已发放」判断改为**互相独立**：管理员中途改了奖励后，玩家下次登录仍能补到新的物品奖励，不会再因为「当天星币已发」被整段跳过；离线补发同理。
7. **修复「补签后连续签到加成激活不了」**：补签原来只把日期补进签到记录、**完全不动连续天数**，所以缺口补上了、加成还是按旧天数算。现在补签后会**从签到记录重算连续天数**（以今天或最后一次签到日为终点向前数，只增不减，不会把已有的更高记录改小），缺口一补上连续天数立刻连成一条，连续签到加成随之生效；补签提示也带上当前连续天数（`补签成功：花费 X，当前连续签到 N 天`）。
8. **日程编辑界面小修**：输入框文字在框内**下移 2px**（原先偏上，看着不居中）；色板 16px → **18px 正圆**（间隙 3px），选中描边同步放大，圆形更明显。
9. **界面点击音效可换 + 当场试听**：提醒音效设置界面最下面新增「**界面点击音效**」一行，点一下就切换并**立刻试听**，共 10 款：模组原音（默认）、木质轻点、原版按钮、石质清脆、机械咔哒、轻打点、清脆铃音、紫水晶、经验球、翻书页。全部使用原版音效（不需要新增音频文件），选择保存在客户端 `config/server_shop_click_sound.txt`，与提醒音效开关互不影响。
10. **付费刷新每日商店加二次确认**：点「刷新」先弹确认框，写清**本次花费**、**今日剩余次数**，并提示「整页卡牌与收购清单会重抽、已购买次数不退」；确认后才扣费刷新，取消 / ESC 原样回到商店界面，什么都不扣。次数已用完时不再弹框（按钮本来就是灰的）。
11. **每日商店翻牌方向**：6 张牌（2 行 3 列）改成**从右往左**翻 —— 缩放轴放在卡牌**右边缘**，视觉上像是从右边翻过来；7 张以上的长条模式改成**从下往上**翻 —— 以长条**下边缘**为轴做纵向翻转（原来是两种模式都从中间横向翻转）。
12. **交易 / 转账的「返回」改成真正回到上一级**：这两个界面的返回以前是「新开一个商店界面」，于是本界面仍然留在返回栈里 —— 回到商店后再按 ESC 就会把它**重新弹出来**。现在返回统一走 `Nav.back()`（回到上一级并把自己从栈里移除）；「玩家摊位」「交易请求」两个界面里同样的返回按钮也一起改掉了。
13. **玩家摊位列表支持滚动**：从「分页」改成和收购 / 货币兑换一致的**整行滚动** —— **鼠标滚轮**上下滑动、**右侧一根蓝色滑块**指示当前位置、**底部还有内容时显示上下浮动的小三角**（已下滑时顶部再补一个向上的小三角）；右上角显示 `当前 / 总数`，原来的「上一页 / 下一页」按钮保留（改成整页上下翻）。
14. **移除「同一个 IP 只允许一个账号登录」的限制**（原 `anti_alt` 配置）：
    * 删掉登录时的 IP 校验（不再把同 IP 的其它账号踢下线）；
    * 删掉 `Config` 里的 `ipAccountLimit` / `ipLimitExemptOps` 两个配置项、`/shop admin ip list|unbind` 子命令、存档里的 IP 绑定表与相关语言文本；
    * 旧的配置文件里如果还留着 `[anti_alt]` 段，模组会直接忽略（不报错），可以手动删掉这一段；
    * 注意：**「同 IP 玩家之间不能转账」这条经济规则仍然保留**（那是防小号刷钱，和登录限制是两件事），如果也要去掉请再说一声。
15. **6 张牌模式的翻牌改回「以卡牌正中为轴」**：上一版改成以右边缘为轴会显得整张牌往右折，现在改回标准的中间轴翻转；长条模式仍是「从下往上」（以下边缘为轴）。
16. **每日商店刷新与每日收购刷新彻底分开**：
    * 两个列表各自一套**每日次数与价格表**：`dailyRefreshCosts`（商店，默认 200/500）、新增 `buybackRefreshCosts`（收购，默认 200/500），次数 = 各自列表长度，可在配置文件里分别调整；
    * 每日收购页面右下角新增「**刷新收购**」按钮（商店的是「刷新商店」），**只重抽收购清单**，不再影响商店卡牌；商店刷新也只重抽卡牌（之前确认框里写的"收购清单也会重抽"是错的，已改正）；
    * 两者**分别计数**（`dailyShopRefreshUsed` / `dailyBuybackRefreshUsed`，每天各自重置）、分别扣费、分别记录流水（备注区分「商店刷新」「收购刷新」）；
    * 「刷新收购」同样带二次确认（写清花费与今日剩余次数），确认框文案与商店的独立。
17. **玩家摊位的返回不再来回循环**：从「逛摊位」进入玩家列表 → 点某个摊位进入商品页后，商品页的「返回 / ESC」以前是"**新开一个**玩家列表"，而列表的返回又弹回商品页 —— 两个界面无限来回。现在：
    * 商品页的「返回 / ESC」统一走 `Nav.backToShop()` —— **直接回商店的「玩家摊位」页**（并把自己和列表一起从返回栈里清掉）；
    * 玩家列表页的「返回」仍是 `Nav.back()`（回到商店），「上架物品」也改成回商店同一页，不再新建重复的商店界面。
18. **界面点击音效统一换成你给的「点击.ogg」**：直接替换模组自带的 `sounds/fy.ogg`（`ui_click` 音效 ID 不变），并把所有界面的点击声接到同一个音效上：
    * 自绘按钮（IOStyle）→ `Bricks.click()`；
    * 原来用原版按钮的界面（发放界面、数量/金额输入、拍卖出价、上架确认）→ 换成新的 `ShopButton`（只改播放的音效，外观行为不变）；
    * 原版确认框 → 换成商店风格的 `ShopConfirmScreen`（iOS 面板 + 是/否，点击音同样统一，中文「是 / 否」）。
    客户端设置文件加了版本号：老配置（之前选过别的点击音）会自动切回这个新默认音。
19. **界面层级重新划分（返回/ESC 不再循环、也不会把关掉的界面弄回来）**：
    * **一级界面**：只有商店主界面（每日商店 / 收购 / 拍卖 / 摊位 / 邮箱 / 兑换 / 商店设置 都是它的页签，切页签不算换界面）——在一级界面按 ESC = 关掉界面。

27. **修复「余额一直显示（已满）」**：
    * **现象**：玩家余额才 840，顶栏却显示 `余额：840星币 （已满）`；
    * **根因**：`wallet.maxBalance` 的范围下限原来是 **1**。服主想「不设上限」把配置写成 `maxBalance = 0` 时，
      NeoForge 会**把越界值纠正到下限 1**（实测：写 0 → 启动后配置被改写成 `maxBalance = 1`，日志同时打印
      `Configuration file … is not correct. Correcting`）。上限变成 1 之后，任何余额 ≥ 1 的玩家都会显示「已满」，
      而且**新的入账会被全部卡住**（`1 - 余额` 为负，等于再也赚不到星币）；
    * **修复**：
      1. `maxBalance` 的范围下限改为 **0**，注释写明「**0 = 不限**」；实测写 0 启动后配置**保持 0**、不再被纠正；
      2. 新增 `Config.maxBalanceLimit()`（`≤ 0` 一律按「不限」返回 `Long.MAX_VALUE`）与 `maxBalanceForClient()`（不限时下发 0），
         所有涉及上限的路径（入账 / 限价 / 发放 / 兑换 / 摆摊 / 拍卖 / 转账 / 交易）**统一走这两个方法**，
         不会再出现「不限」被当成「一分钱都装不下」；
      3. 启动后第一次下发快照时打一行日志：`[模块商店] 余额上限 maxBalance = …（0 或负数 = 不限…）`，
         服主看一眼控制台就知道自己配成了什么；
      4. 顶栏余额的悬停提示补上「**余额上限 X**」，出现「已满」时不用翻配置就知道上限是多少。
    * **已经踩坑的服务器**：若配置文件里已被纠正成 `maxBalance = 1`，改成 `0`（不限）或任意大数字即可，重启生效。

      顶栏余额当场刷新，不会出现「指令说改了、界面还是旧数字」；

29. **修复「数量/金额输入界面点确认后回不去」**：
    * **现象**：管理员在「设置商品（价值/品质/数量）」里点「确认」，数字填对了、服务端也存好了，
      但界面**一直停在输入框上**，玩家以为「确认没生效」，只能按 ESC 或点取消才回得去；
    * **根因**：输入界面（ShopInputScreen）的 confirm() 只对「交易金额」做了返回，
      其它入口（管理员编辑商品 / 出价 / 兑换 / 摆摊改价…）发送完请求就什么都不做；
      而服务端回推的快照又有一条「玩家正开着界面时不抢焦点」的保护，于是没人把这一层关掉；
    * **修复**：confirm() 统一走和「取消」同一条返回路径（Nav.back() + 交易特例），
      确认后立刻回到上一级（管理员编辑 → 商店设置页；摊位购买 → 摊位列表；交易金额 → 交易界面）；
      返回后上一级界面读到的已经是服务端最新数据（价格/品质/数量当场就是新的）；
    * **顺手补反馈**：如果价格填 0 或超上限，原来服务端是静默 eturn（界面一关像什么都没发生），
      现在会红字提示「商品设置未保存：价格需要大于 0 且不超过余额上限 X」。

30. **接入 JEI（鼠标悬停物品 → 按 R / U 看配方与用途）**：
    * **为什么需要单独做**：本模组的界面都是**自绘 Screen**（不是原版容器界面），
      JEI 默认只从原版容器槽位里找「鼠标下的物品」，所以在商店里按 R/U 一直没反应；
    * **做法（纯软依赖）**：新增 JeiPluginImpl（唯一引用 mezz.jei.api.* 的类，带 @JeiPlugin）+
      JeiBridge/JeiHoverSource（**不引用任何 JEI 类型**，没装 JEI 也照常加载）。
      JEI 就绪时把「展示配方」与「按键判定」两个回调注册进 JeiBridge；界面绘制时把「正在显示 tooltip 的那件物品」记下来，
      按键事件（ScreenEvent.KeyPressed.Pre）里读出来交给 JEI：**R = 以「产物」身份查（这东西怎么来的）**、
      **U = 以「材料」身份查（能用来做什么）**；认玩家自己的按键绑定；
    * **覆盖界面**：每日商店（翻开后的卡牌/长条）、每日收购、拍卖会、玩家摊位、摊位商品页、邮箱附件、货币兑换、管理员列表；
    * **不装 JEI 时**：JeiBridge 里没有回调 → 直接返回 false，按键原样传下去，行为与之前完全一致；
      模组也**不打包任何 JEI 代码**（compileOnly），服务器不需要装 JEI；
    * **兼容性**：uild.gradle 已加 JEI 的 maven 与两个 compileOnly 依赖，并**刻意编译 1.21.1 上最早的 19.8.4.110**；
      已逐个 javap 比对 19.8.4 与 19.57 的接口签名（IJeiRuntime / IRecipesGui.show(IFocus) / IFocusFactory.createFocus /
      IJeiKeyMapping.isActiveAndMatches / VanillaTypes.ITEM_STACK）**完全一致**，因此 19.x 任意版本都能用。

40. **反馈修正：加商品报「价格无效」的根因 + 三处界面调整**：
    * **【重要】「价格无效 / 价格需要大于 0 且不超过余额上限 1」的真正原因**：
      早期版本的配置范围下限误写成 `1L`（`defineInRange("maxBalance", 9999999999L, 1L, ...)`），
      NeoForge 加载时会**把配置文件里的 `maxBalance = 0`（0 = 不限）纠正成 1 并写回文件** ——
      于是"不限"变成了"余额上限 1 星币"。而 `parsePrice()` 对**超过余额上限的价格一律返回 0**（防溢出刷钱），
      所以管理员填 5、100、1000 全部被判成"价格无效"，连一件商品都存不下来（与填写的数字是否合法无关）。
      修法（两层，旧配置文件不用手动改）：
      · `Config.maxBalanceLimit()` 把 `<= 1` 一律当作「不限」（1 星币的上限没有任何实际意义，就是那个 bug 的产物）；
      · `ConfigMigration` 启动时把文件里的 `maxBalance = 1` 改写回 `maxBalance = 0`（与另外两条旧默认值迁移一致）；
      · 错误提示改成**说明原因**：填的不是数字 → 「价格无效：请填一个大于 0 的整数」；
        真超过上限 → 「价格超过了余额上限（X），请调小」（新增 `price_over_cap` 文案），不再只回一句"价格无效"。
    * **侧栏的「商店设置」那一行删掉**：模块多起来后它和最后一个模块**画在同一行上互相遮挡**
      （7 个模块时最后一行 y 与该行 y 完全相同）。管理页入口本来就有**右上角那枚「商店设置」药丸**，
      侧栏这行是多余的，删掉后 7 个模块一屏放得下；
      同时给侧栏加了「只画窗口内的 N 行」的硬保护，以后模块再多也只会走滚轮、绝不会压到玩家信息块上；
    * **购物城页去掉底部的「添加物品 / 导入模组」**：上架入口统一收在「商店设置」页里（那页有「添加」与「导入模组」），
      购物城自己的底栏只留翻页 —— 既不再挤底栏，也不会挡住货架；
      空货架提示也简化成「货架是空的」（不再附带管理员操作说明）；
    * **左下角玩家信息块**：头像**下移 2px**，与右侧「名字 + 余额」两行垂直居中；
      余额改成 **0.8 倍字号**绘制（可用宽度按缩放折算，能显示的数字反而更多），
      再长的余额也稳稳在信息块边框以内（以前 1.0 倍字号 + 省略号，看着像顶到了边框上）。

42. **反馈修正：购物城货架翻到第 5 页就翻不动了**：
    * **根因**：管理页的滚轮翻页只算了「每日商店 / 每日收购」两份列表的长度
      （`"buyback".equals(adminMode) ? adminBuyback.size() : adminShop.size()`），
      切到**购物城**时它仍然拿**每日商店的长度**去算总页数 ——
      商店只有 5 页，于是购物城有 22 页也被夹在第 5 页，滚轮再怎么滚都停在 5/22（截图那一幕）；
    * **修复**：翻页上限按**当前编辑对象的列表**算（购物城 → `adminMall`，收购 → `adminBuyback`，否则 → `adminShop`），
      与绘制那一边用的是同一个判断；
    * **顺手修掉同一类的两个隐患**（都是"mode 只认 shop / buyback"留下的）：
      · 打开编辑弹窗时按 mode 取错了列表 —— 编辑购物城的商品会带出**商店另一件商品**的价格 / 品质 / 数量；
      · 管理页「添加条目」发出的 mode 在购物城模式下会被写成 `buyback`（服务端虽然有"当前编辑模块"兜底，
        但一旦没设就会进错列表）。

    * **每日上限的处理方式**：按槽位顺序卖到「今日剩余额度」用完为止，**卖不完的物品留在箱子里**，
      第二天继续结算（不会凭空消失），并提示「今日结算额度已用完」。上限按等级配置，可写 0 = 不限；
    * **升级**：主界面「升级（X 星币）」按钮，花星币提升一级（9 → 18 → 27 格），满级后按钮置灰；

52. **修复「商店数据太大导致客户端掉线」（Network Protocol Error / shop_sync 解码失败）**：
    * **现象**：玩家打开商店时被踢下线，客户端生成
      `disconnect-…-client.txt`，里面写着
      `Failed to decode packet 'clientbound/minecraft:custom_payload'` +
      `Failed decoding custom payload server_shop_mod_1789689358:shop_sync:
      NbtAccounterException: Tried to read NBT tag that was too big;
      tried to allocate: 2097118 + 36 bytes where max allowed: 2097152`；
    * **根因**：原版 `FriendlyByteBuf.readNbt()` 用的是 `NbtAccounter.create(2097152)`，
      也就是**单个 NBT 超过 2 MiB 就直接抛异常**。购物城整包导入（上限 2000 件）之后，
      `shop_sync` 快照一超 2 MiB，**每个打开商店的玩家都会被踢下线**；旧的 `shop_action`
      （客户端→服务端，比如一键导入模组）走的是同一套 `readNbt`，同样会撞上这个上限；
    * **修法（传输层，不管数据多大都不会再撞上限）**：
      新增 `network/NbtTransport` + `network/ChunkAssembler` —— 快照 NBT **先 gzip 压缩**，
      再按 **512 KiB 切片**，每片一个包（同一个 `syncId` + `index/total`），
      接收端集齐后再解压；解压用**自定义上限**（64 MiB）的 `NbtAccounter`，
      不再经过原版 2 MiB 的 `readNbt`。上行（`shop_action`）同样处理，
      所以「整包导入模组」也不会再把玩家踢下线；
    * **顺带更省流量**：gzip 后商店数据（大量重复物品 id）通常只剩原来的几分之一；
      单片上限 512 KiB 也远小于「3 字节 VarInt 长度前缀」的单帧上限（2097151 字节）；
    * **坏包不再踢人**：分包超时（30 秒）/ 超过 64 MiB / 解压失败时**只记一条日志并丢掉这一包**，
      这一次操作不生效而已，下一次打开界面会自动重发（以前是直接 Network Protocol Error 掉线）；
    * **快照瘦身**：`adminShop` / `adminBuyback` / `adminMall` 这些**管理端专用列表只发给管理员**
      （管理页普通玩家打不开），普通玩家收到的快照体积直接砍掉一大截；
    * **兼容性提醒**：载荷通道版本从 `1` 提到 `2` —— **客户端与服务端 jar 必须一起更新**。
      只更新一边时 NeoForge 会直接提示通道版本不一致（一句看得懂的话），
      而不是让旧客户端去解码新格式、再崩成一条「custom_payload 解码失败」。

53. **购物城：新增「定时补货」（库存自动重置）**（管理页 → 购物城 → 「**补货设置**」按钮）：
    * **背景**：购物城原来只有「购买扣库存」，卖完就永远售罄，只能管理员一个个手改 —— 这次补上**定时把卖掉的库存补回去**；
    * **弹窗（4 项，按钮直接点，不用打数字）**：
      ① **定时补货 关/开**；② **时间口径 现实时间 / 游戏时间**；
      ③ **补货时刻**（HH:mm，输入 `0600` 会自动补成 `06:00`，格式不对红字提示且拒绝保存）；
      ④ **补货数量**（`0` = 每件补回**各自原量**，`>0` = 全部**统一补到该数量**）；
    * **「各自原量」怎么来的**：每件商品现在会记住**补货目标** `stockMax` —— 管理员上架 / 编辑 / 导入时填的库存数就是目标，
      卖到 0 之后到点补回这个数；**无限库存（∞）的商品永远不参与补货**，想「限量但不补货」的就把库存设成 ∞；
    * **两种时间口径**（按需求都做成可配置）：
      * **现实时间**：和「每日额度重置」同一套算法（HH:mm 分界，例如设 04:00 则凌晨 3 点还算前一天）；
      * **游戏时间**：和出货箱结算一致（06:00 = 游戏 0 刻）；
    * **每个补货日只补一次**：存档里记 `lastMallRestockDay` / `lastMallRestockGameDay`，
      服务器在补货时刻之后重启**不会重复补**；刚打开开关时只记基准日、不立刻补（避免一开就全场补满）；
    * **玩家看得到**：补货成功后给全服发一条绿字「购物城已补货：N 件商品补回库存」；
      购物城底栏也会显示「**每日补货 00:00（现实时间）**」，售罄时玩家知道只是暂时没货；
    * **配置项**（`[mall]` 段，游戏内改了会直接写回配置文件，手动改配置同样生效）：
      `mallRestockEnabled` / `mallRestockMode`（real|game）/ `mallRestockTime`（HH:mm）/ `mallRestockAmount`（0 = 各自原量）；
    * **兼容旧存档**：老数据没有 `stockMax`，第一次读取时把**当前库存**当成补货目标，不会出现"目标 0 件"导致永远不补。

54. **侧栏滚动动画优化：整列像素级平滑滑动**：
    * 原来滚动是「整行跳」：滚轮一动，每行各自用 `Mth.lerp` 往新槽位靠 —— 行与行同步但**新进/退出的行会突然出现 / 消失**
      （循环只画窗口内的 6 行，滚出去的行当帧就不在循环里了），滚动条也是一格一格跳；
    * 现在改成**两层动画**：
      ① **滚动层**用**像素位移**（`sidebarScrollPx`）逐帧指数逼近目标行（`1 - e^(-dt*22)`，**帧率无关**，
      30 FPS 和高刷屏手感一致），整列一起平移；
      ② **换位层**才用行号插值（`tabSlotAnim`，拖拽排序 / 增删模块时被挤开的页签滑过去）——
      两者互不干扰，所以滚动时不会「发飘」；
    * 因此滚动过程中**上下各多画一行**（正要滑进来 / 正在滑出去），列表带用 `enableScissor` 裁掉带外部分：
      滑进来的行从底部一点点露出来、滑出去的行从顶部消失，**绝不会蹭到左下角玩家信息卡**；
      停下时目标永远是**整行**的整数倍，所以静止状态和以前一模一样（第 0 行贴顶、第 5 行贴底）；
    * **滚动条滑块**也按补间后的像素位置连续移动（不再一格一格跳）；
    * 顺带把拖拽位置的算法统一了：拖动中的页签纵向也换算成「行号」存进同一张表，
      松手后**自动从松手位置滑回真实槽位**（不需要另写回弹动画），横向仍保留自由跟随鼠标的像素偏移。

56. **出货箱：「排序 / 分类」下拉面板不再被清单挡住**：
    * **现象**：点开「排序」或「分类」，面板虽然弹出来了，却被清单里的**物品图标**（胡萝卜 / 马铃薯…）盖住，看着像没弹出来；
    * **原因（和「编辑布局」「购物城下拉」是同一个坑）**：物品图标是 `GuiGraphics.renderItem` 画的
      —— **z = 150 的三维物品渲染**，而且画完立刻 flush **写深度**；下拉面板是 z = 0 的平面填充，
      于是深度测试一挡，后画的面板在图标位置**根本画不上去**（顺序反过来也没用）；
    * **修法**：点开下拉时，被面板矩形挡住的那些行**不再画物品图标与数量角标**（`openDropdownRect()` 算面板矩形，
      逐行做相交判断），面板文字 / 边框 / 高亮照常；面板宽度也从 110 改成**与清单同宽**，看起来就是一张正经菜单；
    * 悬停提示框（`pendingTooltip`）改到**下拉面板之后**绘制，不然面板一开、提示框就被压住；
      顺带把面板的行高 / 宽度 / 分类行数抽成常量（`DD_ROW_H` / `DD_SORT_W` / `DD_CAT_W` / `DD_CAT_ROWS`），
      绘制与命中判定共用一套数字，不会再「画在这里、挡在那里」。

57. **修复：出货箱两条玩家报上来的问题（吞东西 / 加了条目却连别的木头一起收）**：
    * **① 结算「吞东西、钱没到账」——根因是余额上限**：
      `settleShippingBin` 先在循环里**把物品从箱子里扣掉**，最后才 `credit(payout, maxBalance)`；
      而 `credit()` 只会加「余额还装得下的部分」（到顶就返回少加的钱）。于是**余额一满**，
      物品照扣、钱只到账一部分甚至 0 —— 就是玩家反馈的「东西没了钱没来」。
      **实测复现**：箱子 64 个橡木原木、单价 20、余额 95 / 上限 100 → 修复前 `物品 0 / 余额 100`（吞了 64 件只给 5 星币）。
      **修法**：把「余额剩余空间」也当成一种额度（和「今日结算额度」并列，取二者较小值），
      只卖**真的能付得出钱**的那些；余额装不下的**原样留在箱子里**（下次结算继续），
      并给在线玩家一条黄字说明（`shipping_bank_full`）；另加一层兜底：万一个别情况入账仍不足，
      差额转成**金额邮件**（`SOURCE_SHIPPING_UNPAID`），绝不静默销毁。
      **修复后实测**：余额 95 / 上限 100 / 单价 20 → 一件不卖、64 件全在；单价 2 → 只卖 2 件（+4 星币），
      余额 99、箱子剩 62 件 —— 分毫不差。
    * **② 结算时玩家正开着出货箱界面 → 会把卖掉的物品「变回来」（刷物）**：
      结算改的是存档里的 `bin.slots`，而打开着的容器持有**另一份拷贝**，玩家随便动一下格子就会把旧内容整体写回；
      现在结算后如果玩家正开着出货箱，会把界面按存档刷一遍（`syncOpenBin` → `reloadFromBin` + `broadcastChanges`），
      专门用一个「存档 → 界面」方向的方法（不触发 setChanged，否则等于又把旧内容写回去）。
    * **③ 缩容会直接删掉物品**：`ShippingBin.resize()` 以前用 `slots.remove(...)` 砍掉末尾槽位 ——
      只要管理员把配置里的 `shippingLevelSlots` 改小（或玩家 `level` 高于当前等级数），
      每次开箱 / 结算都会把多出来的槽位连物品一起删掉，同样表现为「吞东西」。
      现在改成**先合并进前面的空格 / 同种物品，实在放不下就原样保留在数据里**（宁可多留几格，绝不销毁）。
      实测：27 格各 1 个原木 → 配置改成只剩 9 格 → 物品仍是 27 个（自动并成 19+1+1…）。
    * **④ 「加了橡木条目，别的木头也被收」——其实是规则优先级**：
      规则匹配原来是「**第一条命中的赢**」，而管理页「添加条目」是**追加到列表末尾**的；
      默认规则里本来就有 `#minecraft:logs=3`（**所有**原木都按 3 收），于是新加的 `minecraft:oak_log=6`
      永远排在它后面、**根本不生效**（价格还是 3）。玩家看到"加了橡木条目，其它木头照样能卖"，
      一半是标签规则本身就把所有原木都算进可收清单，一半是这条新规则压根没生效。
      现在改成「**越具体越优先**」：物品规则 &gt; 整模组规则 &gt; 标签规则，同级里写在前面的优先。
      实测：`["#minecraft:logs=3", "minecraft:oak_log=6"]` → 10 个橡木按 **6** 结算、10 个云杉按 **3**，
      合计 90 星币（橡木用自己那条，其它原木继续走标签价）。

58. **修复：出货箱「放进去、重进界面就被清空」（玩家反馈的吞物品）**：
    * **现象**：把物品放进出货箱，关掉界面再打开（或重进服务器后再开），**还没到结算时刻物品就全没了**，
      也没有进账、没有邮件。
    * **根因（容器初始化时"边填边回写"）**：出货箱界面用的容器是 `ShippingBinContainer`，它的
      `setChanged()` 是**把整个容器写回存档**；而 vanilla 的
      `SimpleContainer.setItem()` 内部**会回调 `setChanged()`**
      （源码：`this.items.set(index, stack); stack.limitSize(...); this.setChanged();`）。
      构造函数里原本是「逐格 `setItem(i, bin.slots.get(i).copy())`」——
      于是**第 0 格刚填完就触发一次整体回写**，把「其余 8 格还全是空」的容器写回存档：
      第 1 格之后的物品当场被清空；而循环后续读取的又是**已经被清空的内容**，所以只会越来越空。
      实测复刻（用与香草一致的契约跑一遍）：9 格箱子依次填 9 格 → **触发 9 次回写**，
      打开一次界面后存档变成 `[第 0 格, 空 ×8]` —— 只有第 0 格活下来。
    * **修法**：给容器加一个 `suppressWriteBack` 守卫：**从存档往容器里装载期间**（构造 + 结算后的刷新）
      禁止回写，装完再恢复；`reloadFromBin()`（结算后按存档刷新界面）也走同一个守卫
      （它以前用 `super.setItem`，但 `SimpleContainer.setItem` 调的是虚方法 `setChanged()`，
      照样会回写 —— 只是内容恰好相同才没出事）。
      同样的复刻跑修复后的代码：**装载期间回写 0 次**，箱内容与打开前**完全一致**。
    * 这是同一个坑的第三处（前两处：结算时玩家开着界面会把卖掉的物品"变回来"、缩容会删物品），
      现在三处都收口在「存档 ↔ 容器」这一层，规则是：**装载只读、改格才回写**。

61. **新功能：商店设置 → 摊位 → 下架时间（永久 / 限时，限时支持游戏时间与现实时间）**：
    * **入口**：「商店设置」的模块下拉里现在有 **摊位**；这一页没有「添加条目」（玩家的商品由玩家自己上架），
      只有 **下架时间** 与 编辑布局 两个按钮，并显示当前设置。
    * **三种模式**：
      * **永久**（默认）：商品不会自动下架，行为和以前完全一样；
      * **游戏时间（天）**：上架后超过 `天数 × 24000 刻` 自动下架；
      * **现实时间（小时）**：上架后超过 `小时 × 3600000 毫秒` 自动下架；时长填 0 也等于永久。
    * **剩余时间**：开启限时后，摊位页每件商品的**价格右侧**会显示「剩 X 天 / 剩 X 时 / 剩 X 分 / 即将下架」
      （游戏时间按 24000 刻 = 1 天换算），放不下就自动不画，不会压到按钮。
    * **到期处理（绝不吞物品）**：剩余库存**全部退回** —— 摊主在线直接进背包（背包满自动转邮箱），
      离线则直接进 **邮箱**，并给摊主一条黄字说明「摊位商品「X」已到下架时间，剩余 N 件已退回」。
      售空（库存 0）的商品到期只撤下、没有物品要退。
    * **实现要点**：`StallEntry` 多存两个上架时刻（`listedGame` 游戏刻 / `listedReal` 现实毫秒，随快照一起下发，
      所以客户端能自己算倒计时）；服务端每 20 tick 跑一次 `tickStallExpire`，永久模式立刻短路（零开销）。
      **老存档兼容**：没有上架时刻的老商品会在第一次 tick 时补打时间戳，不会被"立刻下架"，而是给一个完整的限时窗口。
    * **实测（真服务器端到端，两轮）**：往存档里塞一件「2 小时前上架、库存 5」的商品，
      配 `real / 1 小时` → 启动后商品被撤下，**邮箱收到 5 件**（source=`stall_expired`）；
      再塞一件 `listedGame=1`（远古）+ 配 `game / 1 天` → 同样撤下并退回 5 件。
      测试完把存档与配置都还原成原样（摊位 0 条、邮箱 0 封、`permanent` / 7 天）。

    * **实测（真服务器端到端）**：往存档里塞一条「2 小时前发布、悬赏 100 金币」的求购，配 `real / 1 小时`
      → 启动后求购被撤下、**余额 1375 → 1475**（100 金币原样退回），存档里 `demands` 清空。

64. **新功能：商店设置 → 购物城 → 库存设置（库存多久刷新一次）**：

      「库存设置」开着时按钮呈高亮。
    * **两种时间基准**：**现实时间（小时）** 或 **游戏时间（天）**，另外可以选 **关闭**（默认）；
      周期从**上次刷新**算起，到期后**全店库存按每件商品的「原量」补回**（和补货设置里的补货目标一致）。
    * **和「补货设置」的区别**：补货设置是**每天固定时刻**（如 00:00）补一次；库存设置是**每隔 N 小时 / N 游戏天**整店刷新，

    * **第一次运行只记基准**：刚开服 / 刚打开这个设置时不会立刻刷一次库存，避免玩家白拿；之后按周期走。
    * **配置项**（`[mall]` 段）：`mallRefreshMode` = `off` / `real` / `game`，`mallRefreshAmount` = 周期
      （real 按小时、game 按游戏天数，默认 24 / 1 天）；存档记录两套上次刷新时刻，重启不会错乱。
    * **实测**：把「上次刷新」改成 2 小时前 + 周期 1 小时 → 启动后服务端立刻刷新并把时间戳更新为新值
      （`mallRefreshLastReal` 从 0 变成当前毫秒），日志无报错；测完存档与配置已还原。

67. **购物城购买逻辑彻底修正（第 9 条的真实根因）**：
    * **真实根因**：购物城渲染用的是 `mallFiltered()` 的**过滤/排序缓存**，缓存 key 只算了
      「列表长度 + 搜索词 + 分类 + 收藏 + 排序 + 收藏数」，**没算快照本身**。
      买到东西后服务端推来新快照，`ClientShopData.mall` 换成**一批新对象**，而缓存里还留着**旧对象**；
      点卡片时用 `ClientShopData.mall.indexOf(view)` 求下标 → 旧对象在新列表里找不到 → **返回 -1** →
      服务端 `index < 0` 直接 return（没有提示），于是「买完一件后再点别的没反应」，
      只有切页签（缓存 key 变化 / 重建）才恢复。
    * **修法（不再依赖对象身份）**：
      1. `MallView` 新增 `shelf` 字段，解析快照时就写入「它在 mall 列表里的下标」（= 服务端 mallPool 下标）；
      2. 卡片点击 / 收藏都直接用 `view.shelf`，永不 `indexOf`；
      3. `ClientShopData.mallVersion` 每次快照 +1，并加入过滤缓存的 key —— 新快照一到缓存自动失效，
         货架库存数字也能立刻刷新（以前快照后数字会"停在旧值"）。
    * **恢复「点击 → 选数量」**：上一轮为了绕开这个 bug 把单击改成"直接买 1 个"，现在根因修掉了，
      改回**单击商品就弹「买几个」窗口**（左键 / 右键都一样弹窗），与每日商店一致。
    * 实测：构建通过、服务端启动 `Done (8.954s)`、模组报错 0 条、正常关服。

68. **求购选物界面「发糊」修正**：
    * **原因**：那个界面是普通 `Screen`，`renderBackground` 走的是原版逻辑 —— 先把**世界模糊**成背景再垫下来；
      面板又大又半透明，就整片"糊成一片"（截图里文字、物品图标都发虚）。
    * **修法**：重写 `renderBackground`，**不做世界模糊**，直接铺一层实色底（`0xFF0E1013`），
      内容画在上面干干净净；顺带把两个输入框的原版**白色描边**换成自绘的内凹底 + 1px 暗描边，与面板风格统一。
    * 实测：构建通过、启动 `Done (…s)`、模组报错 0 条、正常关服。

69. **求购列表「想要 %s ×%s」乱码 + 字号缩小**：

      于是显示成「想要 %S ×%S」。修法：**直接画 `entry.summary()`**（它自己已经是「物品 ×N」/「物品 ×N 等 M 种」），
      不再重复套模板。
    * **字号缩小**：求购列表（玩家页 + 管理页）的物品行、悬赏行、发布者/倒计时统一改成 **0.8 倍小字**

    * 实测：构建通过；服务端启动正常、模组报错 0 条。

71. **求购交付流程审查 + 加固（扣物品 / 到账）**：
    * **审查结论（正常路径是对的）**：
      * 发布时悬赏**已托管**（金币从余额扣含手续费、副手整叠收走），所以交付方一定拿得到；
      * 交付时先**逐条清点**背包（同物品+同组件匹配），全部够数才扣；扣完把金币 `credit()` 进余额
        （受余额上限约束），装不下的部分转**金钱邮件**；悬赏物品进背包，满则进邮箱；
      * 条目在付款前从列表移除，`handleAction` 在服务端主线程串行执行 → **无法双花 / 重复领取**。
    * **这次修掉的 3 个隐患**：
      1. **扣物品不是原子的**：原来是"逐条扣、哪条失败就把**这一条**已扣的退回"，若第 2 条失败，
         第 1 条已扣的物品就**没退回**（配置变动等极端情况下会吞物品）。现在改成
         **先全部取出记在列表里，只要有一条失败就把已取出的全部退回**；
      2. **付了钱但账单里看不到**：交付入账、撤销/到期退款都没有写交易流水，管理员「交易记录」里查不到。
         现在交付（`求购:发布者`，+金额）与退款（`求购退款`）都会记进 `TransactionLog`；
      3. **离线发布者收不到红点**：`NotificationManager.notify` 原来只在发布者在线时调用。
         现在无论在线与否都会点亮邮箱红点（邮件里说明是谁交付的）。
    * 实测：服务端启动 `Done (5.629s)`、模组报错 0 条、正常关服。

72. **商店界面「关不掉」修复（玩家反馈，午夜刷新时复现）**：
    * **真正原因**：客户端收到快照时有这么一条规则 —— **"只要当前没开界面，就把商店弹出来"**：
      `else if (!silent && minecraft.screen == null) { Nav.open(new ShopScreen(...)); }`。
      平时没人推非静默快照看不出来；但**过了零点**服务端会做一堆自动事（每日刷新、邮件过期清理、摊位到期退还、
      签到自动发放/合并邮件…），这些路径都会顺带推一次**非静默**快照 ——
      玩家刚按 ESC 关掉界面，下一帧/下一秒又被弹回来，表现就是「关不掉」。
    * **修法（加一个显式的"打开"开关，默认绝不抢界面）**：
      1. 快照里新增 `open` 字段，**默认 false**；
      2. `sendSnapshot(player, tab)` / `(…, silent)` 都**只更新数据、绝不弹界面**；
      3. 只有 `sendSnapshotOpen(...)` 才把 `open=true` —— 目前仅 `/shop`、`/shop mailbox`、`/shop stall`、
         `/shop admin` 这四条**玩家主动输入的指令**用它；
      4. 客户端改成 `else if (open && minecraft.screen == null)` 才打开。
    * 效果：关掉商店就是关掉了，午夜刷新 / 邮件合并 / 签到发奖都只更新数据，不会再把界面推回来；
      `/shop` 依然能正常打开。
    * 实测：构建通过、服务端 `Done (5.848s)`、模组报错 0 条、正常关服。

73. **【严重】求购交付后「物品没到发布者手上」——已修（玩家反馈）**：
    * **现象**：B 交付了 A 的求购 → A 的金币被扣（托管）、A 收到一封**求购完成邮件**，但**邮件里没有物品**、
      背包也没收到 —— 物品凭空消失。
    * **根因**：`demandFulfill` 里从 B 背包扣下来的物品只放进了临时列表 `takenStacks`，
      **再也没有投递给 A**：后面只发了一封「求购已完成」的**纯文字通知邮件**（无附件）。
      也就是"扣了 B 的物品，既没给 A、也没退给 B"。
    * **修法**：
      1. 扣完物品后**立刻投递给发布者 A**：A 在线 → `addItemOrMail`（直接进背包，背包满转邮箱）；
         A 离线 → 把所有物品装进**同一封邮件**（`DEMAND_DONE` 草稿 `.addItem(...)`）并点亮邮箱红点；
      2. 在线玩家不再额外收一封空邮件（物品已直投），邮件只作通知；
      3. 邮件模板文案改成「您要的物品已附在附件中（在线时直接进背包）」；
      4. 新增来源标记 `demand_deliver`，便于以后排查。
    * 实测：构建通过、服务端 `Done (8.784s)`、模组报错 0 条。
    * ⚠ **已经发生的损失无法自动找回**（当时物品被直接丢弃、没有留痕）；
      受影响的玩家可以用 `/shop admin` 的「发放物品」把东西补给 ta。

74. **新功能：账单导出（CSV，管理员用）**：
    * **原来**：流水只存在玩家存档里（每人默认 50 条），游戏内能看（玩家点余额的「账单」界面、
      管理员 `/shop admin history <玩家> [页码]` 在聊天栏翻页），**没有任何导出成文件的途径**。
    * **现在**：新增 `BillExporter` + 指令，把流水写成 **CSV**（UTF-8 + BOM，Excel 直接打开中文不乱码），
      落到服务器目录 `config/server_shop_mod/bills/`：
      * `/shop bill <玩家> [起日] [止日]` → `账单-<玩家>-<时间>.csv`
        （表头：时间 / 类型 / **对手方** / 金额 / 交易后余额 / 备注；末尾附**合计收入 / 合计支出 / 净额**）
      * `/shop bill all [起日] [止日]` → `账单-全服-<时间>.csv`（全服所有流水）
        **再加一张** `对账-玩家间-<时间>.csv`：按「玩家A ⇄ 玩家B」聚合成**净额**（双向流水相抵），
        管理员一眼看出谁该给谁多少钱；**系统/管理员/外部来源不计入玩家间对账**。
      * 日期格式 `2026-10-01`；只给权限等级 ≥2（管理员）用；控制台 / RCON 也能执行。
    * **类型本地化**：`trade_in` 这类内部名会转成「交易收入 / 摊位卖出 / 拍卖成交 / 求购悬赏 / 转账支出…」。
    * **实测（真服务器 + RCON）**：
      `shop bill all` → 生成 872 字节全服账单 + 154 字节对账表；`shop bill <玩家名> 2026-09-01 2026-10-31`
      → 生成该玩家 8 条记录的账单；文件内容、日期筛选、对账过滤（只剩玩家↔玩家）均正常。
