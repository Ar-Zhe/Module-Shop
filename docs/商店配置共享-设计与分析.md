# 商店配置导出 / 导入 / 跨世界共享 —— 阶段一（分析）与阶段二（设计）

> 本文只描述**基于现有源码**得出的结论与设计，不含未经验证的假设。
> 代码位置以当前 `main`（1.0.5）为准。

---

## 阶段一：现有商店数据是怎么存的

### 1. 唯一的商店数据源：世界存档（world-scoped SavedData）

```java
// data/ShopSavedData.java:20
public final class ShopSavedData extends SavedData {
    private static final String FILE_ID = "module_shop_data";   // :21

    // :514
    private static final Factory<ShopSavedData> FACTORY = new Factory<>(ShopSavedData::create, ShopSavedData::load);

    // :516-519
    public static ShopSavedData get(MinecraftServer server) {
        DimensionDataStorage storage = server.overworld().getDataStorage();
        return storage.computeIfAbsent(FACTORY, FILE_ID);
    }
}
```

结论：

- 数据落在**当前世界**的 `world/data/module_shop_data.dat`（由 `DimensionDataStorage` 管理），
  和世界存档绑定，**不随整合包、不随客户端、不随玩家账号走**；
- 单人模式里的「服务端」是集成服务器，写的是**当前存档**；
- 换一个新世界 → `computeIfAbsent` 会新建一份空数据，只有 `seedDefaultsIfEmpty()` 的极小默认池
  （苹果 / 面包 / 火把…），所以"新世界没有商品"是**预期行为**，不是 bug。

### 2. 为什么单人配置无法保存到客户端

客户端**根本没有商店数据的持久化**：

- `client/ClientShopData.java` 里全是 `public static` 内存字段，由服务端快照（`ClientboundShopSyncPayload`）填充，
  进程结束即丢失；
- 客户端目前只有两个**非商店数据**的本地文件：
  - `client/ClickSound.java`（`config/module_shop_click_sound.txt`，:55-56 用 `Minecraft.gameDirectory/config` + `version=`）；
  - UI 皮肤（1.0.4 起，`config/module_shop_ui_theme.txt`）。

→ 因此「单人配置能留在客户端、能随整合包分发」这件事，当前架构下**完全没有实现路径**，必须新增。

### 3. 现有商品/模板数据结构（哪些属于"可共享模板"）

| 数据 | 位置 | 性质 |
| --- | --- | --- |
| `shopPool: List<ConfiguredOffer>` | `ShopSavedData:24` | **模板**（每日商店商品池：物品 + `price` + `amount` + 品质） |
| `buybackPool: List<ConfiguredOffer>` | `:25` | **模板** |
| `mallPool: List<MallItem>` | `:27` | **模板**（常驻货架：`price`、库存、`sort`、`stockMax`、个人限购表） |
| `exchangePool: List<ExchangeEntry>` | `:48` | **模板**（货币兑换规则：物品 + 汇率） |
| `shopWeights / shopGuarantee / shopSlotCount` | `:98-102` | **模板**（刷新权重、保底、每日格数） |
| `buybackWeights / buybackGuarantee / buybackSlotCount` | `:104-106` | **模板** |
| `signIn*`（`baseDaily/makeupCost/tiers/miles` 等） | `:78-94` | **模板**（签到参数） |
| `buybackBonusEnabled`、`shopCurrency` | `:73`、`:56` | **模板** |
| `accounts: Map<UUID, PlayerAccount>` | 见 `PlayerAccount:14/34-38` | **运行数据**（余额、刷新次数、奖励领取…）→ **禁止导出** |
| `signIns`、`mallRecent`、`auctions`、`auctionHistory`、`demands`、`redeemCodes` | `:76/29/32/34/46/108` | **运行数据**（个人进度 / 交易 / 邮件 / 兑换码）→ **禁止导出** |

### 4. 管理界面现状（配置管理的落点）

- 商店界面走 1.0.3/1.0.4 的 AtomLib 页面体系：`client/screen/shop/AdminPage.java`（`implements ShopPage`），
  按钮用 `client/ui/widget/Button`，布局在 `render(Canvas, PageFrame)` 里；
- 管理员按钮组已经存在（`moduleBtn / grantBtn / historyBtn / prevBtn / nextBtn`，`AdminPage:44-51`），
  说明「配置管理」加在同一行/新开一页成本很低；
- 协议侧统一走 `ServerboundShopActionPayload`（NBT `action` 字段）+ `ShopManager.handleActionInner` 的 switch。

### 5. 世界生命周期可用钩子

- `event/ShopServerEvents.java`：`onServerStarted(ServerStartedEvent)`（已有，用于启动 HTTP API）、`onServerTick`、`onLogin/onLogout`；
- 世界数据是**惰性**创建的（第一次 `ShopSavedData.get(server)`），所以"首次初始化"必须自己打标记，
  不能靠"文件是否存在"判断（同一个 `.dat` 也会被普通读写刷新）。

## 阶段二：设计

### 1. 数据边界（硬性）

```
客户端模板文件 (可共享)          世界数据 (不可共享)
─────────────────────────       ────────────────────────
商品 / 价格 / 分类 / 顺序        accounts(余额/购买记录)
库存规则 / 刷新权重 / 保底        signIns / mallRecent
签到参数 / 货币名 / 开关          auctions / demands / redeemCodes
格式版本 / 创建时间 / 名称        世界内已完成的交易
```

导出器**只读白名单字段**（上表左列），不 dump 整个 `ShopSavedData`；
导入器**只写白名单字段**，绝不触碰右列。

### 2. 目录与文件

```
<game dir>/config/moduleshop/
├── shop_config.json        客户端默认模板（整合包可直接放这里）
├── backups/                每次覆盖前自动备份（保留最近 N 份）
└── exports/moduleshop_shop_<时间戳>.json
```

> 专用服务器用同一个相对布局（`<server>/config/moduleshop/`），服主也能放模板；服务器仍然 100% 权威。

### 3. JSON 格式（`format_version` 独立于模组版本）

```json
{
  "format_version": 1,
  "mod_version": "1.0.5",
  "created_at": "2026-11-08T12:00:00Z",
  "name": "整合包默认商店",
  "meta": { "note": "可选" },
  "shop":   { "slots": 6, "weights": [5,15,30,50], "guarantee": [0,0,0],
              "offers": [ { "item": "minecraft:apple", "count": 1, "price": 5, "rarity": "common", "amount": 1 } ] },
  "buyback":{ "slots": 6, "weights": [5,15,30,50], "guarantee": [0,0,0],
              "offers": [ ... ] },
  "mall":   { "items": [ { "item": "...", "price": 100, "stock": 16, "stockMax": 16, "sort": 0 } ] },
  "exchange": { "entries": [ { "item": "...", "value": 60 } ] },
  "signin": { "enabled": true, "base_daily": 10, "makeup_cost": 100, "makeup_days": 2,
              "tier_days": [3,5,7], "tier_bonus": [5,7,10], "mile_days": [3,5,7], "mile_money": [100,300,800] },
  "currency": "星币"
}
```

- 物品统一用 `ResourceLocation` 字符串 + 数量；**不存 NBT 组件**（避免跨版本 / 跨模组差异导致崩溃），
  复杂物品若需要保留，用可选 `"nbt"` 字段（base64 NBT），导入时校验失败就跳过该条并计数。
- 只接受**白名单字段**；未知字段忽略但记录。
- 读取端有大小上限（例如 8 MiB）与条目上限（例如 5000/池），防炸。

### 4. 写入安全（对应需求三）

- 原子写：写 `shop_config.json.tmp` → `fsync` → `Files.move(REPLACE_EXISTING)`；
- 覆盖前把旧文件复制到 `backups/shop_config-<时间戳>.json`（保留最近 10 份）；
- 任何异常只**提示失败**，**不删除/不清空**原文件；
- 解析失败时：保留原文件 + 提示"配置损坏，已忽略，未覆盖"。

### 5. 首次初始化（对应需求六，本次重点）

```
ServerStartedEvent
  └─ ShopSavedData.get(server)
       ├─ data.templateInitDone == true  → 什么都不做（已有世界 / 已初始化）
       └─ false → 读 <config>/moduleshop/shop_config.json
                    ├─ 有效  → applyTemplate(REPLACE onto 空/默认池) → templateInitDone = true → setDirty()
                    └─ 无效/缺失 → 保持模组自带默认池 → templateInitDone = true
```

- 只在**世界刚创建**（`templateInitDone=false` 且池子仍等于 `seedDefaultsIfEmpty` 的结果）时生效一次；
  标记存进 `ShopSavedData`（新字段，老存档读成 `false` 时会先按"池子是否仍为默认种子"再判一次，避免覆盖老世界）；
- 单人：集成服务器与客户端同一个 `gameDirectory`，直接读客户端模板；
- 专用服务器：读服务器自己的 `config/moduleshop/`，服主放入即生效；
- 关闭开关：`Config.INSTANCE.templateInitEnabled`（默认 `true`），存档里有 `templateInitDone` 之后永不再执行。

### 6. 权限（对应需求八）

| 动作 | 权限要求 |
| --- | --- |
| 导出（生成文件） | 单机：管理员；服务器：**不生成服务端文件**，只在客户端生成（客户端本地文件，无副作用） |
| 导入到世界 | **服务端**执行，要求 `hasPermissions(2)`；客户端仅发送"应用模板"请求 + 预览数据 |
| 新建世界初始化 | 服务端执行，无需玩家权限（世界创建者） |
| 查看路径 | 客户端只展示自己的路径 |

客户端本地文件**永远不会**被当作服务端数据的来源：导入必须由管理员在游戏内确认，走服务端校验后再写入 `ShopSavedData`。

## 阶段三～七 的推进顺序（对应需求十二）

1. 阶段三：`ShopTemplate` + `ShopTemplateStore`（读写/备份/校验）＋ 单测式的自检路径（临时目录）；
2. 阶段四：导出 / 导入（客户端文件 + 服务端应用）＋ 冲突与无效商品统计；
3. 阶段五：新世界初始化（`templateInitDone` + 启动钩子）；
4. 阶段六：配置管理 GUI（含预览页）；
5. 阶段七：编译 → 起服 → 单人/多人/整合包分发的手工验证清单。

> 阶段三开始前需确认两个取舍（见对话中的提问），确认后按上述顺序实现。
